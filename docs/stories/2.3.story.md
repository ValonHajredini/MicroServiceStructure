## Story

**As a** tenant admin,
**I want** to invite team members via email,
**so that** I can build my organization on the platform.

## Acceptance Criteria

1. POST /users/invite endpoint accepts email, role assignment (admin or user)
2. Invitation token generated and stored with 7-day expiration
3. Email sent with invitation link: mydomain.com/accept-invite?token=xyz
4. GET /users/invite/:token endpoint validates token and returns invitation details
5. User completes registration through invite link, automatically joins tenant
6. Invited user assigned specified role in user_tenant_roles table
7. Expired or invalid tokens show appropriate error message

### Database Schema

**New Table**: `invitations`

[Source: Derived from AC, architecture/database-architecture.md patterns]

```sql
CREATE TABLE invitations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    email VARCHAR(255) NOT NULL,
    role VARCHAR(50) NOT NULL,  -- admin, user
    token VARCHAR(255) UNIQUE NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    invited_by_user_id UUID NOT NULL REFERENCES users(id),
    status VARCHAR(50) DEFAULT 'pending',  -- pending, accepted, expired, cancelled, email_failed
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_invitations_token ON invitations(token);
CREATE INDEX idx_invitations_tenant_id ON invitations(tenant_id);
CREATE INDEX idx_invitations_email ON invitations(email);
CREATE INDEX idx_invitations_status ON invitations(status);
```

**Entity Relationships**:
- invitation.tenant_id → tenants.id
- invitation.invited_by_user_id → users.id
- When accepted: creates user record + user_tenant_roles entry

### Authorization Guards

[Source: architecture/authentication-multi-tenancy.md#security-considerations]

**RolesGuard Implementation** (if not already exists from Epic 1):
```typescript
@Injectable()
export class RolesGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<string[]>('roles', context.getHandler());
    if (!requiredRoles) return true;
    
    const request = context.switchToHttp().getRequest();
    const user = request.user; // From JWT
    
    return requiredRoles.some(role => user.roles?.includes(role));
  }
}
```

**Usage**:
```typescript
@Post('invite')
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('admin')
async inviteUser(@Body() dto: CreateInvitationDto, @CurrentUser() user) {
  // Only admins can access this
}
```

### Business Logic Rules

[Source: AC 1-7, derived requirements]

1. **Duplicate Check**: Before creating invitation, check if user with email already exists in tenant
2. **Pending Invitations**: Only one pending invitation per email per tenant
3. **Token Uniqueness**: Ensure token is globally unique (use DB unique constraint)
4. **Auto-Expire**: Background job (optional) to mark expired invitations as 'expired' status
5. **Email Delivery**: Log email failures but don't block invitation creation

### Error Handling

**Invitation Creation Errors**:
- User already exists: 409 Conflict - "User already member of this organization"
- Pending invitation exists: 409 Conflict - "Invitation already sent to this email"
- Email failure: Log error, mark status as 'email_failed', return 201 success anyway

**Token Validation Errors**:
- Token not found: 404 Not Found - "Invalid invitation link"
- Token expired: 400 Bad Request - "Invitation has expired"
- Token already used: 400 Bad Request - "Invitation has already been accepted"

### Security Considerations

[Source: architecture/security-architecture.md, architecture/authentication-multi-tenancy.md#security-considerations]

1. **Token Security**: Use cryptographically secure random tokens (crypto.randomBytes)
2. **Token Single-Use**: Mark invitation as 'accepted' after registration to prevent reuse
3. **Expiration**: Strictly enforce 7-day expiration
4. **Email Verification**: Invitation serves as email verification (user must access their email)
5. **Rate Limiting**: Limit invitation requests to prevent spam (e.g., 10 per admin per hour)
6. **HTTPS Required**: Invitation link must use HTTPS in production

### Multi-Tenancy Handling

[Source: architecture/authentication-multi-tenancy.md#multi-tenancy-implementation]

1. **Tenant Context**: Invitation created in context of admin's tenant (from JWT)
2. **Automatic Assignment**: New user automatically assigned to inviter's tenant
3. **Role Assignment**: Role from invitation determines user's permissions
4. **Tenant Isolation**: Users can only invite to their own tenant
