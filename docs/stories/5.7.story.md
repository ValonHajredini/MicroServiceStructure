# Story 5.7: E2E Testing Suite

## Status
Draft

## Story

**As a** QA engineer,
**I want** end-to-end tests covering critical user journeys,
**so that** we catch regressions before production.

## Acceptance Criteria

1. E2E framework configured: Playwright or Cypress (decision made by Week 4)
2. Test suite 1: User registration → Login → Dashboard navigation → Logout
3. Test suite 2: Create note → Add attachment → Search note → Delete note
4. Test suite 3: Create Kanban board → Add columns → Create task → Move task → Add comment
5. E2E tests run in CI/CD pipeline before production deployment
6. Test reports generated showing pass/fail status with screenshots on failure
7. Cross-tenant isolation test: Verify Tenant A cannot access Tenant B's data

## Tasks / Subtasks

- [ ] Task 1: Select and Bootstrap Framework (AC: 1)
  - [ ] Evaluate Playwright vs Cypress and document selection rationale by Week 4
  - [ ] Scaffold tests within monorepo (e.g., `apps/e2e-tests/`) with shared configuration
  - [ ] Configure environment management for staging/prod URLs and credentials

- [ ] Task 2: Implement Authentication Journey Tests (AC: 2)
  - [ ] Automate user registration, login, dashboard verification, and logout flows
  - [ ] Include assertions verifying JWT issuance and dashboard widgets load
  - [ ] Capture screenshots and traces on failure

- [ ] Task 3: Implement Notes Journey Tests (AC: 3)
  - [ ] Automate note creation, attachment upload (DigitalOcean Spaces), search, and deletion
  - [ ] Validate UI reflects actions and backend data persists
  - [ ] Clean up test data post-run

- [ ] Task 4: Implement Kanban Journey Tests (AC: 4)
  - [ ] Automate board creation, column management, task creation/movement, and comment addition
  - [ ] Verify drag-and-drop interactions and toast notifications when applicable
  - [ ] Ensure tests resilient to real-time updates introduced in Story 4.10

- [ ] Task 5: Cross-Tenant Isolation Validation (AC: 7)
  - [ ] Create tenants A and B; ensure user from Tenant A cannot access Tenant B resources through UI/API
  - [ ] Include negative test cases hitting APIs directly to confirm backend enforcement
  - [ ] Log evidence of access denial responses

- [ ] Task 6: CI/CD Integration & Reporting (AC: 5, 6)
  - [ ] Add E2E job to GitHub Actions pipeline (Story 5.2) executing on staging deployments
  - [ ] Publish HTML/PDF reports and failure screenshots as artifacts
  - [ ] Update documentation detailing how to run E2E suites locally and in CI

## Dev Notes

### Previous Story Insights
- Story 5.6 deployed production infrastructure; leverage staging environment created during deployment pipeline for E2E executions and ensure monitoring alerts incorporate E2E results.  
  [Source: docs/stories/5.6.story.md#tasks--subtasks]

### Data Models
- Tenant-aware entities must be seeded for tests; rely on multi-tenant schema definition when creating fixtures for notes and kanban data.  
  [Source: architecture/database-architecture.md#multi-tenancy-pattern]

### API Specifications
- Use REST endpoints and authentication flows defined in architecture when scripting API interactions or verifying system state post-UI actions.  
  [Source: architecture/api-contracts-communication.md#api-design-principles]

### Component Specifications
- Tests should align with UI and service responsibilities: Core handles auth/dashboard, Notes manages note CRUD, Kanban handles board workflows.  
  [Source: architecture/component-architecture.md#core-service]  
  [Source: architecture/component-architecture.md#notes-service]  
  [Source: architecture/component-architecture.md#kanban-service]

### File Locations
- Place E2E project under `apps/` or `tests/` directory consistent with monorepo expectations; store shared helpers in `libs/` if needed.  
  [Source: architecture/architecture-decision-records.md#adr-008-monorepo-with-nxturborepo]

### Testing Requirements
- Architecture does not provide dedicated testing standards; incorporate screenshots, trace artifacts, and cleanup steps to meet acceptance criteria.

### Technical Constraints
- Authentication and tenant isolation rules from security docs must be respected and validated within tests to prevent cross-tenant data leakage.  
  [Source: architecture/authentication-multi-tenancy.md#security-considerations]  
  [Source: architecture/security-architecture.md#threat-model]

### Testing Standards

- Run E2E suites against staging before every production deployment and block release on failures.  
- Capture artifacts (screenshots, videos, traces) and upload to CI for debugging.  
- Schedule nightly E2E runs to catch regressions outside release cadence.
