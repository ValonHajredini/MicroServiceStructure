# Story 5.2: GitHub Actions CI/CD Pipeline

## Status
Draft

## Story

**As a** developer,
**I want** automated testing and deployment pipeline,
**so that** code changes are validated before reaching production.

## Acceptance Criteria

1. GitHub Actions workflow triggered on pull requests to develop/main branches
2. Turborepo cache configured for optimized builds (only rebuild changed services)
3. Pipeline stages: lint → test (unit + integration) → build → deploy (staging/production)
4. Unit and integration tests run for all changed services
5. Deployment to staging on merge to develop branch
6. Deployment to production on merge to main branch (manual approval gate)
7. Pipeline failure notifications via GitHub (email or Slack integration optional)

## Tasks / Subtasks

- [ ] Task 1: Define Workflow Strategy (AC: 1, 2, 3)
  - [ ] Review existing monorepo configuration (Nx/Turborepo) to understand task pipelines and caching options
  - [ ] Determine workflow file names and triggers for PRs, develop branch merges, and main branch merges
  - [ ] Document stages aligning with lint → test → build → deploy lifecycle

- [ ] Task 2: Author CI Workflow for Pull Requests (AC: 1, 2, 3, 4)
  - [ ] Create `.github/workflows/ci.yml` triggered on `pull_request` to `develop` and `main`
  - [ ] Configure `actions/setup-node@v3` with Node 18 and enable caching using Turborepo remote or local caches
  - [ ] Add lint and unit/integration test jobs using `npm run lint` and `npm run test:all` (or service-specific scripts)
  - [ ] Upload test reports as workflow artifacts for traceability

- [ ] Task 3: Implement Staging Deployment Workflow (AC: 3, 4, 5)
  - [ ] Extend workflow or create separate `.github/workflows/deploy-staging.yml` triggered on `push` to `develop`
  - [ ] Reuse build artifacts (Docker images, compiled Angular assets) produced by CI stage
  - [ ] Deploy to staging infrastructure (DigitalOcean App Platform or Droplets) using `doctl` and environment-specific credentials
  - [ ] Verify post-deployment health by hitting staging `/health` endpoints

- [ ] Task 4: Implement Production Deployment Workflow (AC: 3, 4, 6)
  - [ ] Configure workflow triggered on `push` to `main` requiring manual approval (`environment: production` with reviewers)
  - [ ] Promote staging artifacts to production to avoid rebuild drift
  - [ ] Execute deployment commands and include rollback guidance (e.g., re-deploy previous tag)
  - [ ] Capture deployment status for audit in workflow summary

- [ ] Task 5: Configure Secrets, Cache, and Notifications (AC: 2, 7)
  - [ ] Document required GitHub secrets (DigitalOcean tokens, JWT secrets, Slack webhook optionally)
  - [ ] Enable `actions/cache` or Turborepo remote caching keyed by lockfile hash and workspace scope
  - [ ] Configure GitHub notification settings and optional Slack/MS Teams webhook for failures
  - [ ] Ensure sensitive data never logged in workflow output

- [ ] Task 6: Validation & Documentation (AC: 3, 5, 6, 7)
  - [ ] Test workflows via draft pull request and branch merges to confirm triggers and approvals
  - [ ] Update `docs/deployment/github-actions.md` (create if missing) with pipeline overview, secrets list, and troubleshooting
  - [ ] Record evidence of successful staging and production runs for story completion

## Dev Notes

### Previous Story Insights
- Story 5.1 established Dockerfiles and Compose orchestration. Reuse generated image tags and environment variable conventions when building and deploying in pipeline to avoid configuration drift.  
  [Source: docs/stories/5.1.story.md#tasks--subtasks]

### Data Models
- Pipeline does not alter schemas. Ensure database migrations run during deployment via existing TypeORM commands before promoting releases.  
  [Source: architecture/infrastructure-deployment.md#cicd-pipeline-github-actions]

### API Specifications
- Services expose REST endpoints; pipeline health checks should target `/health` or equivalent endpoints defined per service to validate deployment success.  
  [Source: architecture/component-architecture.md#core-service]

### Component Specifications
- Monorepo uses Nx/Turborepo enabling shared tooling and build targets. Configure workflows to execute only affected projects while honoring shared libraries.  
  [Source: architecture/architecture-decision-records.md#adr-008-monorepo-with-nxturborepo]

### File Locations
- GitHub Actions workflows reside under `.github/workflows/`. Deployment scripts may live in `tools/` or `scripts/` directories if additional automation is required.  
  [Source: architecture/infrastructure-deployment.md#cicd-pipeline-github-actions]

### Testing Requirements
- Architecture docs do not include a dedicated testing-strategy file. Follow acceptance criteria to execute lint, unit, and integration commands for all impacted services within the workflow and surface reports as artifacts.

### Technical Constraints
- Pipeline sample specifies Node 18 environment, Docker builds for each service, and DigitalOcean deployment using `doctl`. Align with these standards and ensure secrets management through GitHub environments.  
  [Source: architecture/infrastructure-deployment.md#cicd-pipeline-github-actions]
- Maintain JWT and tenant isolation considerations by ensuring environment variables used during deployment match authentication guidelines.  
  [Source: architecture/authentication-multi-tenancy.md#security-considerations]

### Testing Standards

- Simulate pull request runs to confirm lint/test stages execute for affected projects and caching reduces runtime.  
- Validate staging deployment workflow completes automatically on develop merges and surfaces deployment logs.  
- Validate production workflow enforces manual approval and notifications fire on success/failure through GitHub or configured webhooks.
