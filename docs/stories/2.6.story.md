# Story 2.6: File Upload Service

## Status
Draft

## Story

**As a** service (Notes, Kanban, Forms),
**I want** centralized file upload capability,
**so that** I can handle attachments consistently across services.

## Acceptance Criteria

1. POST /files/presigned-url endpoint generates DigitalOcean Spaces presigned URL
2. Request includes: fileName, fileSize, mimeType, targetService (notes, kanban, forms)
3. Presigned URL scoped to tenant: bucket/{tenantId}/{service}/{fileId}
4. URL valid for 15 minutes
5. File metadata stored in files table: id, tenant_id, service, file_name, file_size, uploaded_by, created_at
6. GET /files/:id returns file metadata and download URL
7. DELETE /files/:id marks file as deleted (soft delete) and removes from Spaces

### Database Schema

**File Metadata Table**

[Source: architecture/database-architecture.md#file_metadata]

```sql
CREATE TABLE file_metadata (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    uploaded_by_user_id UUID NOT NULL REFERENCES users(id),
    filename VARCHAR(255) NOT NULL,
    file_size BIGINT NOT NULL,  -- bytes
    mime_type VARCHAR(100),
    storage_key TEXT NOT NULL,  -- DigitalOcean Spaces key
    storage_url TEXT NOT NULL,  -- Full URL (optional, can be generated)
    service VARCHAR(50) NOT NULL,  -- notes, kanban, forms
    status VARCHAR(50) DEFAULT 'pending',  -- pending, active, deleted
    created_at TIMESTAMP DEFAULT NOW(),
    deleted_at TIMESTAMP
);

CREATE INDEX idx_file_metadata_tenant_id ON file_metadata(tenant_id);
CREATE INDEX idx_file_metadata_uploaded_by ON file_metadata(uploaded_by_user_id);
CREATE INDEX idx_file_metadata_service ON file_metadata(service);
CREATE INDEX idx_file_metadata_status ON file_metadata(status);
```

**Status Values**:
- `pending`: Upload URL generated, file not yet uploaded
- `active`: File successfully uploaded and confirmed
- `deleted`: File soft deleted (can be purged later)

### Presigned URL Generation

[Source: AWS SDK documentation, AC 3, 4]

**Upload URL (PUT)**:
```typescript
import { PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

async generateUploadUrl(
  storageKey: string,
  mimeType: string
): Promise<string> {
  const command = new PutObjectCommand({
    Bucket: process.env.DO_SPACES_BUCKET,
    Key: storageKey,
    ContentType: mimeType,
    // Optional: Add metadata
    Metadata: {
      'tenant-id': tenantId,
      'uploaded-by': userId
    }
  });

  return await getSignedUrl(this.s3Client, command, { 
    expiresIn: 900  // 15 minutes
  });
}
```

**Download URL (GET)**:
```typescript
import { GetObjectCommand } from '@aws-sdk/client-s3';

async generateDownloadUrl(storageKey: string): Promise<string> {

    Key: storageKey
  });

    expiresIn: 900  // 15 minutes
  });
```

### File Name Sanitization

[Source: Security best practices]

```typescript
sanitizeFileName(fileName: string): string {
  // Remove path traversal attempts
  const baseName = fileName.replace(/^.*[\\\/]/, '');
  
  // Remove special characters except dots, dashes, underscores
  const sanitized = baseName.replace(/[^a-zA-Z0-9._-]/g, '_');
  
  // Limit length to 200 characters
  return sanitized.substring(0, 200);
}
```

### Client-Side Upload Flow

**Frontend Implementation**:

```typescript
// upload.service.ts
async uploadFile(
  file: File,
  targetService: string
): Promise<FileMetadata> {
  // Step 1: Get presigned URL
  const response = await this.http.post<PresignedUrlResponse>(
    `${API_URL}/files/presigned-url`,
    {
      fileName: file.name,
      fileSize: file.size,
      mimeType: file.type,
      targetService
    }
  ).toPromise();

  // Step 2: Upload to Spaces using presigned URL
  await this.http.put(response.data.uploadUrl, file, {
    headers: {
      'Content-Type': file.type
    }
  }).toPromise();

  // Step 3: Confirm upload (optional)
  await this.http.patch(
    `${API_URL}/files/${response.data.fileId}/confirm`,
    {}
  ).toPromise();

  return response.data.metadata;
}
```

### File Deletion Strategy

[Source: AC 7]

**Soft Delete Approach**:
```typescript
async deleteFile(fileId: string, userId: string): Promise<void> {
  const file = await this.fileMetadataRepo.findOne({ 
    where: { id: fileId } 
  });

  // Verify ownership or admin rights
  if (file.uploaded_by_user_id !== userId && !isAdmin) {
    throw new ForbiddenException();
  }

  // Soft delete in database
  await this.fileMetadataRepo.update(fileId, {
    status: 'deleted',
    deleted_at: new Date()
  });

  // Immediately delete from Spaces (or schedule for later)
  await this.deleteFromSpaces(file.storage_key);
}

private async deleteFromSpaces(storageKey: string): Promise<void> {
  const command = new DeleteObjectCommand({
    Bucket: process.env.DO_SPACES_BUCKET,
    Key: storageKey
  });

  await this.s3Client.send(command);
}
```

**Alternative**: Schedule deletion for later (e.g., cron job that purges deleted files after 30 days).

### Security Considerations

[Source: architecture/security-architecture.md, architecture/authentication-multi-tenancy.md]

1. **Tenant Isolation**: Files scoped by tenant_id in storage path and database
2. **Access Control**: Users can only access files from their tenant
3. **Presigned URL Expiration**: 15 minutes limits exposure window
4. **Content-Type Enforcement**: Presigned URL includes Content-Type header requirement
5. **File Size Limits**: Prevent storage abuse (25MB max per file)
6. **Mime Type Whitelist**: Prevent malicious file uploads
7. **Rate Limiting**: Limit upload requests per user
8. **Virus Scanning**: Consider ClamAV integration for production (optional)

### Multi-Tenancy Handling

[Source: architecture/authentication-multi-tenancy.md#multi-tenancy-implementation]

1. **Automatic Scoping**: tenant_id extracted from JWT and used in storage path
2. **Database Filtering**: All queries filtered by tenant_id
3. **Access Validation**: Verify user's tenant_id matches file's tenant_id
4. **Service Scoping**: Files organized by service (notes/kanban/forms)

### Error Handling

**Upload Errors**:
- File too large: "File size exceeds maximum allowed size of 25MB"
- Invalid type: "File type not supported. Allowed types: images, PDFs, documents"
- Invalid service: "Invalid service name. Must be: notes, kanban, or forms"
- Network error: "Upload failed. Please try again."

**Download Errors**:
- Not found: "File not found or has been deleted"
- No access: "You don't have permission to access this file"
- Expired: "Download link expired. Please request a new link."

**Delete Errors**:
- No permission: "Only file owner or admin can delete files"
- Already deleted: "File has already been deleted"

### Performance Considerations

[Source: architecture/scalability-performance.md]

- **Target**: File upload <5 seconds for 25MB files
- **Strategy**: Direct upload to Spaces (bypass server)
- **Presigned URLs**: Client uploads directly to Spaces, no server bandwidth used
- **Expiration**: Short-lived URLs prevent abuse
- **Cleanup**: Background job to remove abandoned pending uploads
