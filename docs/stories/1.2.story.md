### JWT SSO Pattern Overview

[Source: architecture/authentication-multi-tenancy.md#jwt-based-sso-flow]

**The pattern to validate:**

1. **Login Flow:**
   - User submits credentials to auth-service
   - Auth-service validates and generates JWT with claims
   - JWT returned to client, stored in localStorage

2. **Service Access Flow:**
   - Client includes JWT in Authorization header: `Bearer <token>`
   - Each service validates JWT using shared secret (HS256) or public key (RS256)
   - Service extracts tenantId and user context from validated token

3. **Token Structure:**
```typescript
{
  sub: "user-uuid",           // User ID
  email: "user@example.com",
  tenantId: "tenant-uuid",
  roles: ["admin"],
  enabledServices: ["notes", "kanban"],
  iat: 1234567890,           // Issued at
  exp: 1234654290            // Expires (24 hours)
}
```

### JWT Validation Implementation

[Source: architecture/authentication-multi-tenancy.md#jwt-based-sso-flow]

**JwtStrategy Pattern (to be implemented in POC):**

```typescript
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: process.env.JWT_SECRET  // HS256 approach
      // OR for RS256:
      // secretOrKeyProvider: (request, rawJwtToken, done) => {
      //   done(null, PUBLIC_KEY);
      // }
    });
  }

  async validate(payload: JwtPayload) {
    return {
      userId: payload.sub,
      email: payload.email,
      tenantId: payload.tenantId,
      roles: payload.roles,
      enabledServices: payload.enabledServices
    };
  }
}
```

### HS256 vs RS256 Decision Criteria

[Source: architecture/authentication-multi-tenancy.md#security-considerations]

**HS256 (Symmetric):**
- ✅ Simpler implementation
- ✅ Faster token generation/validation
- ⚠️ Shared secret across all services
- ⚠️ Secret rotation affects all services simultaneously

**RS256 (Asymmetric):**
- ✅ Only auth-service needs private key
- ✅ Other services only need public key
- ✅ Better security model for microservices
- ⚠️ More complex key management
- ⚠️ Slightly slower performance

**POC Must Test:**
- Implementation complexity for both approaches
- Performance differences (token generation and validation)
- Key distribution and management requirements
- Suitability for our microservices architecture

### Security Considerations

[Source: architecture/security-architecture.md#security-checklist]

**JWT Security Requirements:**
- Token expiration: 24 hours (configurable via env var)
- Secret management: Use environment variables, NEVER hardcode
- Algorithm: Explicitly specify (prevent "none" algorithm attack)
- Token validation: Check signature, expiration, and claims

**Testing Requirements:**
- Valid token accepted by resource-service
- Expired token rejected
- Invalid signature rejected
- Missing token rejected
- Tampered payload rejected
