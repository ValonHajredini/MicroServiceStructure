# Story 2.4: User Join Request Flow

## Status
Ready for Review (QA fixes applied - awaiting re-review)

## Story

**As a** user,
**I want** to search for organizations and request to join,
**so that** I can access my company's workspace.

## Acceptance Criteria

1. GET /tenants/search?name=query endpoint returns matching tenant names (public search)
2. POST /tenants/:id/join-requests creates join request record with status: pending
3. Tenant admins see pending requests in dashboard notifications
4. PATCH /tenants/join-requests/:id endpoint allows admin to approve/reject request
5. Approved request creates user_tenant_roles entry granting access
6. Rejected request notifies user via email with reason (optional)
7. User can only have one pending request per tenant at a time

### Database Schema

**New Table**: `join_requests`

[Source: AC 2, 7, architecture/database-architecture.md patterns]

```sql
CREATE TABLE join_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    status VARCHAR(50) DEFAULT 'pending',  -- pending, approved, rejected
    message TEXT,  -- Optional message from user
    admin_response TEXT,  -- Optional response from admin on rejection
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Prevent duplicate pending requests
CREATE UNIQUE INDEX idx_join_requests_unique_pending 
ON join_requests(tenant_id, user_id) 
WHERE status = 'pending';

CREATE INDEX idx_join_requests_tenant_id ON join_requests(tenant_id);
CREATE INDEX idx_join_requests_user_id ON join_requests(user_id);
CREATE INDEX idx_join_requests_status ON join_requests(status);
```

**Important**: Unique constraint only applies to pending requests. Same user can have multiple historical requests (approved/rejected).

### Business Logic Rules

[Source: AC 1-7, derived requirements]

1. **Public Search**: Anyone can search for tenant names (no authentication required)
2. **Authentication for Request**: Must be logged in to request to join a tenant
3. **Duplicate Prevention**: Cannot have multiple pending requests to same tenant
4. **Already Member Check**: Cannot request to join if already a member
5. **Admin Authority**: Only admins of target tenant can approve/reject
6. **Role Assignment**: Approved users get 'user' role by default (not admin)
7. **Status Finality**: Once approved/rejected, request cannot be modified

### Search Implementation

[Source: AC 1]

**Case-Insensitive Search**:
```typescript
async searchTenants(query: string): Promise<Tenant[]> {
  return this.tenantsRepo
    .createQueryBuilder('tenant')
    .where('LOWER(tenant.name) LIKE LOWER(:query)', { 
      query: `%${query}%` 
    })
    .andWhere('tenant.status = :status', { status: 'active' })
    .select(['tenant.id', 'tenant.name'])
    .limit(20)
    .getMany();
}
```

### Role Assignment on Approval

[Source: AC 5, architecture/database-architecture.md#user_tenant_roles]

When admin approves join request:
```typescript
async approveJoinRequest(requestId: string, adminUserId: string) {
  const request = await this.findOneOrFail(requestId);
  
  // Create user_tenant_roles entry
  await this.userTenantRolesRepo.save({
    user_id: request.user_id,
    tenant_id: request.tenant_id,
    role: 'user' // Default role for joined users
  });
  
  // Update request status
  request.status = 'approved';
  await this.joinRequestsRepo.save(request);
  
  // Optionally send email notification
  await this.emailService.sendJoinRequestApproved(request);
}
```

### Security Considerations

[Source: architecture/security-architecture.md]

1. **Rate Limiting**: Prevent search abuse with rate limiting (10 req/min)
2. **Public Endpoint Security**: Search endpoint is public but only returns minimal data (id, name)
3. **Admin Verification**: Always verify admin belongs to target tenant
4. **Status Validation**: Only allow actions on 'pending' requests
5. **SQL Injection**: Use parameterized queries (TypeORM handles this)
6. **Information Disclosure**: Don't reveal if tenant exists in error messages (use generic errors)

### Multi-Tenancy Handling

[Source: architecture/authentication-multi-tenancy.md]

1. **Request Scoping**: Join request links user to tenant
2. **Role Assignment**: Approved users get 'user' role (can be upgraded later)
3. **Tenant Isolation**: Admins can only see/manage requests for their tenant
4. **Cross-Tenant Prevention**: User cannot bypass approval process
